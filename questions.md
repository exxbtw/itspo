# Ответы на вопросы для самопроверки

1. Какие критерии вы использовали при разделении на микросервисы?

я разделил все по зонам ответственности. notifications-svc отвечает за хранение и выдачу уведомлений, а sender-svc только за отправку. Если нужно заменить способ отправки, не нужно трогать основной сервис. Плюс если sender-svc упадёт, уведомления продолжат создаваться, просто не будут отправляться.

2. Почему выбрали именно этот стек?

Python и FastAPI — потому что это то, с чем мы работали на протяжении курса. FastAPI автоматически генерирует документацию и есть валидация через Pydantic. gRPC выбрал для межсервисного взаимодействия, потому что это строго типизированный контракт через proto-файл — сразу видно что принимает сервис и что возвращает. nginx как шлюз — база.

3. Как сервисы справляются с ошибками?

Реализован graceful degradation: вызов sender-svc обёрнут в try/except с таймаутом 3 секунды. Если sender-svc недоступен, notifications-svc логирует WARNING и всё равно возвращает клиенту 201. Т.е. падение сервиса отправки не ломает создание уведомления. 

4. Как организован деплой без простоя?

CD реализован через GitHub Actions — при пуше в main срабатывает deploy job, который применяет kubectl apply -f k8s/ и ждёт успешного завершения rollout. Zero downtime обеспечивается RollingUpdate стратегией в deployment.yaml: replicas: 2, maxUnavailable: 0 — при обновлении сначала поднимается новый под, только потом гасится старый, сервис всегда доступен.

5. Что было самым сложным в интеграции?

Самым сложным было разобраться как правильно реализовать CD этап. Не сразу было понятно как связать GitHub Actions с Kubernetes — нужно было понять что пайплайн должен не просто собирать образ, но и деплоить его в кластер через kubectl apply. Плюс разобраться с RollingUpdate стратегией. Ещё был момент с proto-файлом — оба сервиса используют один и тот же .proto, но лежат в разных папках, пришлось выставить build context в корень проекта чтобы Dockerfile мог его достать.

6. Что бы улучшили, если бы был ещё месяц?

добавил бы нормальную бд для хранения уведомлений. Мб подключил бы RabbitMQ между notifications-svc и sender-svc вместо прямого gRPC вызова.
